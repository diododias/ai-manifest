# Skill: Business Discovery

Transforms the transcription of an agenda (you + PM) into business requirements
structured and **accumulative**. Each calendar updates a living document per
feature — not one-shot extraction.

## Problem you solve

Transcripts lose implicit context: how you and the PM already share
history, the agenda only talks about a part of the demand and references things without
define ("that flow we talked about"). This skill accumulates the context
of previous agendas in the document and (b) explicitly **flags** the
unresolved references rather than inventing.

##Input

- **Required:** path (or content) of the agenda transcription.
- **Optional:** feature name/slug (if you can't infer, ask).
- **Optional:** materials that the PM brought (PRD, mockup, spreadsheet).

## Output

Document in `business-discovery/<feature-slug>/requisitos.md`, using
`templates/requisitos.md` of this skill. Consult
`templates/exemplo-preenchido.md` just as a filling reference.

## Artifact contract

Before writing, please follow [the shared agreement](../references/workflow-contract.md).
The above path is the default; use the consumer repository convention if it
exist.

## Steps

### 1. Identify the feature
Enter the content slug (ex: `lista-de-espera`). If ambiguous, **ask**
before proceeding. Target: `business-discovery/<feature-slug>/requisitos.md`.

### 2. Load baseline
If the file already exists, read it in its entirety — it is the accumulated context of the agendas
previous ones. Every extraction from this agenda is a **delta** against this baseline.
If it doesn't exist, this is the feature's first schedule.

### 2.5. Transcription cleanup (if VTT)
If the input file is a raw `.vtt` generated by meeting tools (Teams, Meet, Zoom), **before processing**, run the helper cleanup script to remove timestamps and reduce token consumption.
Command to be executed in the terminal:
`python3 scripts/business-discovery-clean-vtt.py <caminho_do_vtt> -o <caminho_do_vtt_limpo.txt>`
Then read the generated `.txt` file and use it as a basis for extraction. If the transcript is already clear text, skip this step.

### 3. Extract from transcript
Raise (quoting excerpts when useful):
- **User stories** — who, wants what, for what. Capture **priority** if
  agenda gave a signal (P1 = MVP, without it it does not deliver value; P2/P3 = increments).
- **Scenarios (Given / When / Then)** — for each story, testable examples
  said on the agenda. **Then** is the observable result; if it hasn't been said, it is
  gap — **don't invent the result**. Include the exception path when quoted.
- **Business rules** — pay attention to the spoken marker "business rule"
  business:". Normalize each with precondition + trigger + "the system must" + response.
  Each rule needs a concrete example; If the example or any clause is missing, record it as a gap — **do not invent a number,
  value nor trigger**. Point out which scenario verifies it.
- **Success criteria (measurable)** — business metrics with and without numbers
  technology (SC-XX). Vague adjective ("quick", "easy") without a number is a gap.
- **Flows** — happy path and exceptions / edge cases (empty, limit, competition).
- **Decisions** made on the agenda.
- **Questions** raised and not resolved.
- **New domain terms** → glossary (mark uniqueness/identity if required).
- **Out of scope** explicitly stated.

### 4. Diff against the baseline
For each item, rate:
- **new** — did not exist in the baseline.
- **changed** — refines/changes an existing item (show before → after).
- **contradicted** — conflicts with the baseline. DO NOT overwrite silently: record the
  conflict and raise it as a doubt (DA-XX) to confirm in the next agenda.

Reuse existing numbers (RN-XX, US-X); just create a new number for the item
new.

### 5. Detect gaps (gap detection)
This is the part that increases assertiveness. List on `⚠️ Gaps detectados`:
- **Unresolved references** — "that flow", "just like the other email", "from
  the way we did it": something mentioned but not defined in this transcription or in the
  baseline. Say what you assumed (if you assumed) and check "confirm".
- **Rules without concrete example.**
- **Scenarios without a clear "Then"** — story or rule without a defined observable result.
- **Business rule without scenario** that verifies it (Given/When/Then).
- **Incomplete rule** — no trigger/precondition, or "must" with vague answer.
- **Success criterion without number** — metric with vague adjective instead of target.
- **Questions without owner/deadline** → becomes DA-XX.

If you needed to assume something to close a rule, that is a gap — record it.

### 6. Write the document
Update `requisitos.md` following the template. Rules:
- **Current Consolidated State:** Keep the final, consolidated version of the requirements at the top of the document. If there are changes or resolved contradictions in the new agenda, update this consolidated state to reflect the final decision.
- **Changelog is append-only and is at the end:** Add a new entry with the agenda date and the delta summary (new/changed/contradicted) at the end of the document to serve as an audit history. Never delete previous entries.
- Update header (date, agenda list, status).
- Keep the sections in the template order.

### 7. Report in chat
Return, short:
- Delta summary (X new rules, Y changed, Z contradicted).
- The list of `⚠️ Gaps` + `DA-XX` — **the questions to take on the next agenda.**

Don't solve the gaps by inventing; the value is the list of questions.

## Conventions

- `RN-XX` business rules (aligned with the project's RN-30).
- `US-X` user stories (with priority `P1`/`P2`/`P3`) · `SC-X` criteria
  measurable success · `DA-X` open doubts (with owner + deadline).
- Scenarios in Gherkin pt-BR: **Given** / **When** / **Then** (+ **And** / **But**).
- Rules (RN) structured in Portuguese (marker "the system **must**"):
  **While** (state), **When** (event), **Where** (optional), **If…then**
  (unwanted), ubiquitous (no keyword), compound (While+When). ⚠️ "When/Then"
  appear in rules and in Gherkin — the RN is declarative with "must"; the scenario is
  sequence Given→When→Then.
- Status: 🟡 in discovery · 🟢 ready to specify · ✅ turned into spec.
- Write in Portuguese. Prefer numerical example to vague description.

## Handoff for review-prd and create-spec

The `requisitos.md` is the discovery artifact — powers the skill
[`review-prd`](../review-prd/SKILL.md) when the feature turns 🟢, and then the
skill [`create-spec`](../create-spec/SKILL.md) for the technical specification. O
format mirrors the PRD produced by these skills so the passage is direct:

| business-discovery | PRD/SPEC |
|---------------------------|----------------------------------------|
| US-X + D/Q/E Scenarios | User Scenarios → Acceptance Scenarios |
| Priority P1/P2/P3 | User Story priority |
| RN-XX | Functional requirements |
| SC-XX | Success criteria |
| Glossary / domain | Key entities |
| Flows → exceptions | Edge cases |
| Out of scope | Out of scope |

Structured RN ≈ functional requirements ("the system must..." follows the same
structure), so the RN→requirement conversion is almost 1:1.

The open `⚠️ Gaps` and `DA-XX` saw pending clarification in the PRD/SPEC —
resolve it on the agenda before specifying.

## Before the agenda

Use `templates/roteiro-agenda.md` from this skill to prepare the agenda — it
forces the implicit context to be made explicit, which otherwise does not enter the transcription.
The better the script is followed, the fewer gaps the skill needs to flag.
