# Maturity

Maturity in AI-assisted software development is the ability of a squad to turn a real problem into a measurable product outcome **repeatedly, safely and sustainably**. It is not the number of AI tools in use, the percentage of code generated by a model or how little human participation remains. Faster code generation without product clarity, engineering discipline and fast feedback only produces more work in progress and more defects sooner.

This page provides a complete model for assessing a squad, choosing the next improvement and deciding how much autonomy its current system can sustain. It applies to a product or value stream — the end-to-end path from a need to an observed production outcome — regardless of language, platform, process framework or AI provider.

## How to read the model

The unit of assessment is the **squad operating a product or value stream**, not an individual, a model or an isolated repository. Maturity is a profile across dimensions, not a single vanity score.

Four rules keep the assessment honest:

1. **Levels are cumulative.** A squad only sustains a level when the practices from previous levels still work.
2. **Observed behavior outweighs declared process.** Use evidence from a recent, representative window, not a checklist of tools purchased or documents created.
3. **Do not average away a critical weakness.** A strong platform does not compensate for an unsafe release process; excellent automation does not compensate for an unknown user outcome.
4. **Autonomy follows risk and evidence.** A mature squad may automate a reversible, well-observed change and still require human judgment for an irreversible or ambiguous decision.

A four-to-twelve-week window is usually enough for an initial baseline. Use a longer window for low-frequency releases or rare incidents.

## The six dimensions

| Dimension | The question it answers | Evidence of maturity |
|---|---|---|
| **Product and user value** | Do we know whose problem is being solved and whether the result helped? | explicit outcomes, product telemetry, user feedback, guardrail metrics and decisions tied to evidence |
| **Flow and work design** | Can an idea move in small, visible and reversible batches? | limited work in progress, explicit states, short feedback loops, manageable batch size and known blockers |
| **Engineering quality and reliability** | Can the squad change the system without transferring risk to users? | version control, automated verification, secure defaults, operability, service-level objectives (SLOs), progressive delivery and recovery practice |
| **Knowledge and data** | Can people and AI retrieve current, authoritative context? | canonical sources, decision history, discoverable contracts, healthy data, provenance and freshness controls |
| **Platform and automation** | Does the environment make the correct path the easiest path? | self-service workflows, reproducible environments, observable pipelines, reusable capabilities and clear feedback |
| **Human-AI collaboration and governance** | Are tasks allocated, reviewed and escalated according to their risk? | explicit AI stance, authorized tools and data, independent review, traceable outputs, learning loops and accountable owners |

Assess every dimension separately. A useful result looks like `Product M2 · Flow M3 · Quality M2 · Knowledge M1 · Platform M2 · Collaboration M1`. That profile shows the bottleneck. A single label such as “we are M3” hides it.

## The maturity ladder

| Level | Operating model | Role of AI | Role of people | Evidence that the level is real |
|---|---|---|---|---|
| **M0 — Opportunistic** | work depends on individual effort and implicit knowledge | occasional, ungoverned assistance | compensate manually for missing process and context | isolated examples, with no comparable baseline |
| **M1 — Assisted** | basic work is visible and repeatable | copilot for bounded tasks under direct review | specify, execute and verify every material decision | versioned work, basic tests, explicit ownership and an initial metrics baseline |
| **M2 — Standardized** | the squad shares practices, context and quality criteria | performs recurring steps through approved tools and patterns | design the workflow, review exceptions and improve standards | small batches, shared definitions, automated checks and comparable delivery data |
| **M3 — Integrated** | product, engineering and operation form one measured flow | coordinates bounded work across stages and systems | set outcomes, resolve ambiguity and make risk-based decisions | end-to-end traceability, product telemetry, self-service platform and independent gates |
| **M4 — Governed autonomy** | multiple flows operate concurrently within explicit policies | executes and coordinates reversible work within delegated authority | govern policies, handle exceptions and decide high-impact trade-offs | policy enforcement, least privilege, evidence, progressive delivery, rollback and sustained stability |
| **M5 — Adaptive** | the socio-technical system improves itself through controlled experiments | selects tools and strategies within measured boundaries | set direction, challenge the system and approve structural change | causal experiments, continuous learning, dynamic routing and better outcomes without degraded safeguards |

### M0 — Opportunistic

AI use begins through personal initiative. Prompts, decisions and useful context stay with whoever performed the task. Work arrives in large batches, validation is mostly manual and the squad cannot tell whether AI improved delivery or merely increased output.

The objective at M0 is not autonomy. It is visibility: select one value stream, identify the user outcome, put code and configuration under version control, make work states explicit and record a baseline before changing the process.

**Typical failure:** treating tool access as transformation and scaling an unmeasured practice across the organization.

### M1 — Assisted

AI is a supervised assistant. It may explain code, draft tests, summarize evidence or propose a small change, but a person provides the context and verifies material output before it moves forward. Ownership, acceptance criteria and the source of truth are explicit.

The squad has a reproducible path for basic changes, automated checks for the most common failures and a small set of delivery, quality and product metrics. The goal is to make good work repeatable before making it autonomous.

**Ready to advance when:** comparable work follows the same path and variation caused by missing context or missing checks is visible.

### M2 — Standardized

The squad no longer depends on individual prompting technique. Recurrent activities have shared procedures, reusable context and clear entry and exit criteria. Changes are small, work in progress is controlled, approved AI tools are known and sensitive data has an explicit policy.

Automation covers deterministic verification; people focus on ambiguity and judgment. AI-assisted and non-assisted work can be compared without ranking individuals. Failed checks, rework and escalations feed improvements to the workflow.

**Ready to advance when:** the standardized path reduces cycle time or toil without increasing failed changes, escaped defects or human correction effort.

### M3 — Integrated

Discovery, planning, implementation, review, release and observation become one traceable flow. Product outcomes shape priorities; operational feedback returns to planning. AI can coordinate bounded tasks across tools because context, interfaces, permissions and expected outputs are explicit.

The platform provides reproducible environments and fast feedback. Human checkpoints are positioned where risk or ambiguity demands judgment, not where automation happens to stop. The squad can connect a production outcome back to the decision, change and evidence that produced it.

**Ready to advance when:** end-to-end flow remains predictable across several release cycles and independent controls catch known failure modes.

### M4 — Governed autonomy

Specialized agents may plan and execute reversible work, operate concurrently and deliver through progressive exposure. Authority is bounded by policy, data classification, risk class and environment. Identity, provenance, evidence and cost travel with every material change.

People supervise the system rather than every step. They own policy, architecture, product direction and exceptions. Automatic rollback or containment limits impact when observed behavior crosses a predefined boundary.

**Ready to advance when:** greater delegated autonomy produces better outcomes and lower friction over a sustained window without degrading stability, security or accountability.

### M5 — Adaptive

The squad treats its operating model as a product. It tests changes to prompts, models, context, workflow and platform with a baseline, a hypothesis and guardrails. Routing can adapt to risk, cost and task type; knowledge and controls evolve when evidence reveals drift.

M5 does not mean “no humans”. It means human attention is concentrated on direction, novel judgment and structural change while routine, observable and reversible decisions are handled at the appropriate level of automation.

**Evidence of M5:** improvement is attributable to controlled changes in the system, not to more model usage, more output or a temporary effort spike.

## Promotion, regression and autonomy

A capability is ready to advance only when three kinds of evidence agree:

| Evidence | What must be true |
|---|---|
| **Capability** | the required practice, skill, platform path or control exists and has an owner |
| **Behavior** | the squad actually uses it on representative work, including exceptions and failure paths |
| **Outcome** | speed, quality, value, cost or team experience improves while its guardrails remain healthy |

Promotion is a decision about a specific dimension and scope, not a permanent badge. Reassess after a material platform, architecture, team or policy change. Repeated bypasses, stale context, worsening stability or missing telemetry justify regression until the capability is restored.

Autonomy is also contextual. A squad may sustain M4 automation for dependency updates and remain at M2 for pricing, privacy or data-migration decisions. The mature behavior is to use the highest **supported** autonomy for the risk at hand, not the highest technically possible autonomy.

## Running an assessment

1. Choose one product or value stream and name its users, services and squad boundary.
2. Collect a baseline from the same definitions and sources for four to twelve weeks.
3. For each dimension, find the highest level supported by capability, behavior and outcome evidence.
4. Record the profile, evidence, gaps and confidence; use `unknown` when telemetry is missing.
5. Select the lowest risk-critical dimension as the next constraint to improve.
6. Run one bounded improvement experiment with an owner, target, guardrail and review date.
7. Reassess after the window; keep, change or reverse the intervention based on the result.

The output should be a short improvement backlog, not a certification exercise. If the assessment produces dozens of simultaneous initiatives, it has failed to identify the constraint.

## A practical first 90 days

| Window | Focus | Expected result |
|---|---|---|
| **Days 0–30** | choose a value stream, define the outcome and guardrails, publish the AI stance, inventory data and establish the baseline | the squad can describe its current system with evidence |
| **Days 31–60** | reduce batch size, make work and ownership visible, standardize recurring tasks, automate common checks and capture AI involvement | comparable work follows a repeatable path |
| **Days 61–90** | remove the largest measured bottleneck, delegate one low-risk activity and compare outcome, stability, effort and cost | one capability advances without weakening another |

## What maturity is not

- AI adoption rate, seats purchased, prompt count, token volume or generated lines of code.
- A ranking of people, squads or agent roles.
- A checklist that can only move upward.
- Maximum automation in every decision.
- A substitute for product strategy, engineering judgment or accountability.

Current DORA research describes AI as an amplifier of the surrounding organizational system and highlights user focus, small batches, strong version control, healthy data, AI-accessible context, a clear AI stance and a quality internal platform as enabling capabilities. This model turns those ideas into a cumulative operating path; it does not require adopting any particular framework or provider.
