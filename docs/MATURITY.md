# Maturity

[Gates](GATES.md#progressive-autonomy-and-the-harness-ceiling) establishes the ladder and the rule that governs it: the harness level is the ceiling of autonomy, never its consequence. This page makes the ladder operable — what each level requires item by item, and how a repository finds out which level it is actually at rather than which one it believes it is at.

The autonomy levels the ladder grants, A0 through A4, are defined in [Human checkpoints](metodologia/02-checkpoints-humanos.md).

## The level is computed, not declared

A maturity level is a claim, and every item below is written so that a script can check it. This is the whole design constraint of this page: a checklist that requires judgment gets answered optimistically by whoever is being asked, and a repository's stated level is otherwise a record of the day someone last thought about it.

Two rules follow from making it mechanical:

**The level is the minimum, not the average.** A repository satisfying every HL2 item except branch protection is at HL1. There is no partial credit, because the missing item is exactly the one an incident will find.

**A declared degraded mode lowers the level while it lasts** ([Failure](FAILURE.md#declaring-a-degraded-mode)). A quarantined gate is a missing gate for as long as the quarantine holds.

## HL1 — readable

The agent can understand the repository and check its own work locally.

| Item | Checkable by |
|---|---|
| `AGENTS.md` at the root, with all six blocks present | file exists; each block heading found; escalation block non-empty |
| `docs/rules/` with at least `architecture.md` and `testing.md` | files exist and are non-empty |
| `testing.md` maps change type to mandatory levels | the mapping table is present ([Rules](RULES.md#the-testing-strategy-as-a-rule)) |
| `scripts/verify.sh` exists and accepts `--staged`, `--affected`, `--full` | invoke each with `--help` or a dry run |
| `verify.sh` fails on a known-bad input | run it against the canary fixture |
| `verify.sh` asserts its own tools are installed | remove a tool from PATH; expect failure, not a skip |
| `.hooks/` with a pre-commit sensor, plus bootstrap that sets `core.hooksPath` | `git config core.hooksPath` returns `.hooks` after bootstrap |
| Secret scanning runs in pre-commit | the fake-credential fixture is rejected |
| `.agent/settings.json` with `allowed` / `ask` / `denied` and a budget | file parses; `allowed` is non-empty; no wildcard over a command family |

## HL2 — verifiable

A clean environment reproduces the verification, and the result of a change is auditable by someone who did not produce it.

| Item | Checkable by |
|---|---|
| CI fast lane and deep lane as separate configurations | both files exist; neither is editable by the flow it gates |
| Fast-lane path filters have a test | the filter test exists and runs ([Failure](FAILURE.md#verifying-the-verifier)) |
| Branch protection: no direct push to the default branch, required status checks | query the platform API, not the documentation |
| `CODEOWNERS` covering `.agent/`, `.hooks/`, CI configuration and `docs/rules/` | every path matches an owner that still exists |
| Evidence pack generated by `scripts/evidence.sh` | run it; the directory contains `summary.md`, `verify-output.txt`, `gate-status.json` |
| `gate-status.json` distinguishes `passed`, `failed`, `skipped` | all three states are producible |
| `.agent/mcps.json` exists, or the repository declares that no MCP is authorized | file exists, or the explicit zero-scope statement does |
| `.agent/trust.md` declares which paths are instruction | file exists; the instruction path list is exhaustive |
| `HARNESS_VERSION` and `.agent/CHANGELOG.md` | both exist; the version parses ([Versioning](VERSIONING.md)) |
| A known-bad canary for the architecture and secret gates | both canaries run on a schedule and are currently passing |

## HL3 — operable by a team

Several agents operate the repository at once, and the controls hold without a person in each loop.

| Item | Checkable by |
|---|---|
| A distinct identity per agent role that writes | the identities exist and differ; commits are signed |
| The merge gate rejects approval by an author of the same change | attempt it on a test change; expect rejection |
| `attestation.json` produced and validated at merge | the merge gate fails on a missing or mismatched attestation |
| Repository skills in `skills/<skill>/SKILL.md` | the recurring procedures of this repository are covered |
| The agent holds no production credential | the credential inventory shows deploy secrets only in the pipeline identity |
| Post-deploy baseline and an automatic rollback criterion | the criterion is declared and has been exercised at least once |
| Evidence freshness checked before integration | a stale pack is rejected by the merge queue ([Concurrency](CONCURRENCY.md)) |
| A budget per Work Item, not only per invocation | exceeding it escalates rather than truncating |
| Escape rate recorded per gate | the field exists and has been populated by real findings ([Metrics](METRICS.md)) |

## `harness-doctor`

Every row above is a check, and the set of checks is a script. `scripts/harness-doctor.sh` runs them and reports the level the repository actually reached:

```
$ scripts/harness-doctor.sh

HL1  readable          9/9   ✓
HL2  verifiable        8/10  ✗
     ✗ branch protection: default branch accepts direct push
     ✗ canary: no known-bad fixture for the architecture gate
HL3  operable by team  2/9   ✗

Level: HL1        Sustained autonomy: A0–A1
Currently operating at: A2   ← ceiling exceeded
```

The last line is the output that matters. Comparing the computed level against the autonomy actually being granted turns the central rule of the ladder from a principle into an alarm — and it is the check that no repository performs on itself by accident.

Run it in the deep lane and on a schedule. A repository does not usually fall down the ladder by decision; it falls when a group in `CODEOWNERS` is deleted, a path filter stops matching, or a tool leaves the image.

## Getting to the next level

The order is not a preference. Each layer removes a class of failure that makes the next one measurable, and building out of sequence produces controls that cannot be trusted:

| Build | Before | Because |
|---|---|---|
| `AGENTS.md` and the rules | any automation | an agent without an entry contract improvises, and you are then automating the improvisation |
| `verify.sh` and the sensors | CI | CI that does not match the local check produces failures no one can reproduce |
| The canaries | granting autonomy on green | a gate that has never rejected anything has not been shown to work |
| Evidence and attestation | multiple agents | with several agents in flight, "who produced this and against what" stops being answerable from memory |
| Identity and branch protection | unattended merge | separation of duties is structural or it does not exist |
| Metrics | promoting the level | promotion on artifacts alone measures intent, not capability |

**The first week of a bare repository** is the first two rows and nothing else: write `AGENTS.md` with an honest escalation block, write the two rule files, make `verify.sh` real, install the pre-commit sensor with secret scanning, and add the tool-installation assertion so none of it can silently stop running. That is HL1, it supports A0–A1, and it is worth more than an HL3 checklist filled in aspirationally — because at HL1 the ceiling and the practice agree, which is the only property that makes any of the levels mean anything.
